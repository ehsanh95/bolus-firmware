Quick hardware-test workflow

  1. Select only the parameters you intend to change. Command order matters: put an Acquisition Level preset BEFORE individual sensor overrides in a combined message.
  2. Use a new Transaction ID for each new command. Reuse the most recently accepted ID only when deliberately testing duplicate suppression.
  3. Queue Base64 as Unconfirmed, FPort 3 in ChirpStack. A Class A node receives the downlink in an RX window following an uplink.
  4. Decode the FPort 4 response. result=0 means the packet was accepted, NOT that hardware apply is finished. Check pending_apply_mask=0, failed_apply_mask=0, and actual sensor or gateway behavior.
  5. Avoid Pause/Breakpoints during radio-window and interval tests. Never include ABP credentials in screenshots or reports.

Motion / Event

BMA456
Any-motion — values, effects & verification

Controls BMA456 Any-Motion interrupt sensitivity; it does not configure the step counter. The named presets adjust BOTH the acceleration threshold and required duration. Lower thresholds/shorter durations typically detect smaller, briefer movement but may increase false positives. RAW depends on separately provisioned raw parameters; this form only selects the mode.

Allowed value / rangeConfiguration effectPractical impact
0 · RAWConfigured raw threshold / duration / cooldownEngineering calibration only; not a ready-made preset.
1 · VERY_LOW900 mg · 800 msHighest threshold and longest duration; conservative detection.
2 · LOW750 mg · 600 msSlightly easier to trigger.
3 · LEVEL_1600 mg · 500 msModerate sensitivity.
4 · LEVEL_2500 mg · 400 msNormal acquisition preset.
5 · LEVEL_3400 mg · 300 msHigher sensitivity.
6 · LEVEL_4300 mg · 200 msHighest named preset; assess false positives.
7 · OFFInterrupt disabledMotion episode initiation by this detector is suppressed; other functions may continue.

How to verify: Read bma_event_service_diag_profile, threshold_mg, duration_ms and interrupt_enabled, then compare controlled motion events and false triggers. Event enable and acquisition preset can override the final behavior.

Step counter — values, effects & verification

Independent BMA456 step-detection profile. This firmware presently accepts only DEFAULT, LEVEL_1 and LEVEL_7; levels 2–6 have driver mappings but are not approved by RuntimeConfig validation. The levels below are Bolus-specific settings, not factory Bosch labels.

Allowed value / rangeConfiguration effectPractical impact
0 · DEFAULTKeep the sensor feature-engine defaultsBaseline for comparative trials; inspect readback.
1 · LEVEL_1Step parameter 5 = 10; parameter 13 = 1Most robust accepted preset; may miss small steps but can reduce false steps.
7 · LEVEL_7Step parameter 5 = 4; parameter 13 = 0Most sensitive accepted preset; may increase false step counts.
2–6Not currently acceptedDo not infer their accuracy from the driver mapping alone.

How to verify: Read bma456_diag_step_params_valid, bma456_diag_step_param5/13. Walk a counted route and compare step deltas on successive telemetry windows; a correct write does not prove step-detection accuracy.

Retrigger guard — values, effects & verification

Minimum spacing used to suppress repeated motion pulses inside an episode. Increasing the guard reduces duplicate activity triggers but can suppress genuinely separate rapid events; shortening it has the opposite effect.

Allowed value / rangeConfiguration effectPractical impact
0 msNo extra retrigger guardRapid successive motion may be recorded.
>0 to 60,000 msTimed suppression windowChoose based on event dynamics; value must be below the quiet timeout in milliseconds.

How to verify: Trigger two known pulses within and beyond the guard; inspect event_episode_retrigger_suppressed_count, pulse counts and the resulting episode digest.

Quiet timeout — values, effects & verification

Closes a motion episode after the configured no-activity interval, subject to episode logic. A shorter interval closes episodes sooner but can split one episode into several; a longer interval merges intermittent activity and delays deferred sensor reconfiguration.

Allowed value / rangeConfiguration effectPractical impact
1–3,600 sSyntactic rangeOther cross-field rules also apply.
Typical default 120 sLonger episode continuityMust exceed configured temperature follow-up deadlines (latest default: 65 s) and must not exceed the maximum episode duration.

How to verify: Use known pulse timing and verify event_episode_closed_count, final digest, and how long pending sensor apply waits during an active episode.

Sets a coordinated power/observation preset for BMA event detection, TMP117, MPU triggering and event processing. IMPORTANT: the preset resets raw BMA event parameters and overwrites sensor-specific choices; when combining it with custom sensor commands, place the preset FIRST.

0 · Boundary onlyPERIODIC TMP, conversion cycle 7, BMA/MPU event triggers offMinimum background observation; event pipeline disabled.
1 · Very lowHYBRID TMP cycle 7; BMA VERY_LOWBoth sentinels on with conservative motion trigger.

Controls independent TMP117 HIGH/LOW alert monitoring and the application's temperature strategy; it does not mean all periodic temperature acquisition disappears.

Allowed value / rangeConfiguration effectPractical impact

TMP high limit — values, effects & verification

Signed integer in hundredths of a degree Celsius (centi-°C). Lowering the high threshold makes high-temperature alerts occur sooner; raising it delays them. Cross-field validation requires high > low.

Allowed value / rangeConfiguration effectPractical impact
4,10041.00 °C (repository default)Reference high-alert threshold.
4,00040.00 °C (validated in combined bench test)Earlier high-temperature warning than 41 °C.
-5,500 to 15,000Supported overall numeric limitsThe actual lower bound must also remain above the current low limit.

How to verify: Read sensor_service_config.temperature.high_limit_centi_c; independently check sensor register/alert behavior. RAM success alone does not validate a physical temperature excursion.

TMP low limit — values, effects & verification

Signed centi-°C. Increasing it triggers low-temperature alerts sooner during cooling; decreasing it tolerates colder readings before alerting. The low value must remain strictly below the high value.

Allowed value / rangeConfiguration effectPractical impact
3,50035.00 °C (repository default)Reference low-alert threshold.

How to verify: Read sensor_service_config.temperature.low_limit_centi_c and, if relevant, measure low-alert assertion/clear at a safe reference temperature.

TMP background period — values, effects & verification

Defines scheduled temperature-read spacing for PERIODIC mode. It does not control the conversion-cycle register in HYBRID sentinel mode, and it does not set the LoRaWAN uplink period. This command has NO dedicated live-reinitialization apply bit in the current handler.

Allowed value / rangeConfiguration effectPractical impact
1–86,400 sShorter = more frequent scheduled reads; longer = less frequentMeaningful when temperature.strategy=PERIODIC.
600 sRepository defaultUseful baseline when experimenting with background reads.

How to verify: Check sensor_service_config.temperature.sample_period_s, strategy and timestamps of actual reads, rather than relying on ACCEPTED_NO_LIVE_RECONFIG alone.

MPU burst length — values, effects & verification

Length of high-detail inertial acquisition following a qualifying event. Short bursts cost less active time but can miss longer motion; long bursts capture more context but increase active sampling and may affect low-power behavior.

Allowed value / rangeConfiguration effectPractical impact
100–500 msValidated configuration rangeChoose with expected event duration.
250 msRepository defaultBaseline for comparing captured samples and energy.

How to verify: Check mpu_service_ready, burst counters/sample count and sensor power-gating following the burst; verify no interference with radio-critical windows.

MPU trigger — values, effects & verification

Determines whether eligible events start an MPU6050 burst. This does not necessarily turn off independent scheduled MPU operations or BMA motion detection.

Allowed value / rangeConfiguration effectPractical impact

Stored as a radio-policy configuration value, 500–10,000 ms. This is NOT the LoRaWAN RX1/RX2 window period. IMPORTANT: the current live LoRaWAN service does not use this field to replace its existing TX watchdog deadline; physical impact remains unverified.

Retry delay — values, effects & verification

Wait time before retrying after selected transmission failures. Lower values make retries quicker but may exacerbate MAC busy/energy load; higher values give the channel more time but delay queued telemetry.

Allowed value / rangeConfiguration effectPractical impact
0 msImmediate eligible retryUse cautiously; does NOT bypass EU868 duty-cycle rules.
1–60,000 msIncreasing backoff intervalBalancing responsiveness and retry pressure.
2,000 msRepository defaultValidated as a configuration bound; timing stress test remains separate.

How to verify: Watch tx_retry_count, tx_failure_count, next_action_tick_ms and gateway reception during controlled intermittent link failures.

Max TX attempts — values, effects & verification

Bounds retry attempts for applicable application/control responses. Fewer attempts reduce worst-case retry activity but drop earlier on a bad link; more attempts improve opportunities for delivery at the cost of airtime/energy.

Allowed value / rangeConfiguration effectPractical impact
1Single attemptFail/drop early when an attempt fails.
2–4Intermediate retry budgetsSelect based on measured link conditions.
5Maximum accepted settingHigher retry budget; not a guarantee of delivery.

How to verify: Observe tx_retry_count, tx_failure_count, tx_drop_count and control-response counters under intentionally impaired RF conditions.

Reading FPort 2, FPort 4, and apply diagnostics

FPort 2 — telemetry: The active V3 summary contains acquisition_level, the CUSTOM flag, schema version, validity flags, temperature, battery and activity counts. Continuation packets carry additional episode digests. runtime_config_version=12 is the schema number, not the number of successful configuration changes.

FPort 4 — response: Exactly eight bytes: D2 01 [TXID] [RESULT] [APPLY_MASK_LE16] [SCHEMA_LE16]. Result 00 means accepted with pending work; 02 is a duplicate of the most recently accepted transaction ID. The response's apply mask lists required work; it is NOT the live pending mask.

Errors and atomicity: 83 length, 84 unknown command, 85 value and 86 invalid complete configuration. A malformed command in a multi-command request rejects the WHOLE RAM commit.

RF and ADR: A requested SF in RuntimeConfig and s_requested_datarate do not prove the physical SF. Compare actual gateway DR/SF with ADR state. Battery: a zero reading under 3.3 V programmer power without the battery connected is outside battery-validation scope, not proof that the ADC pathway passes.

Open verification items

  • RF: Control ADR and correlate the actual PHY rate with MIB state close to transmission; preserve gateway reachability.
  • BMA456: Verify motion trigger accuracy and step-counter accuracy for permitted sensitivity presets using a known stimulus, not ACK alone.
  • Robustness: Test downlink during an active episode, RX1 and RX2 separately, response backlog and an uninterrupted STOP2 endurance run.
  • Coverage: Truncated/wrong-port packets and remaining command IDs still require complete hardware-level records; local runtime settings are RAM-only.

Qualification boundary: These results validate the listed bench scenarios; they do not establish full protocol-command, RF PHY, energy, or production readiness. A zero battery voltage was observed while the board was powered from the programmer rather than its battery input; the battery ADC has not been separately qualified.
