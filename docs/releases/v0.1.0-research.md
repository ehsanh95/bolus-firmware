# Bolus Firmware v0.1.0-research

**Status:** Research release — not production-ready  
**Source branch:** `test/functional-downlink`  
**Target snapshot branch:** `research/v0.1.0`

This is the first research release of the Bolus firmware. It freezes the current dual-sentinel sensing architecture, Episode-based event model, Telemetry V4 transport, configurable downlink path, and STOP2 low-power work into a reproducible research snapshot.

## Scope

Hardware target:
- STM32L476
- BMA456
- TMP117
- MPU6050
- RFM95W / SX1276
- LoRaWAN EU868 Class A

Network ports:
- FPort 2 — telemetry
- FPort 3 — application downlink configuration
- FPort 4 — downlink ACK/NACK

## Research architecture

The firmware uses two independent low-power sentinels:

- **BMA456** for Any-Motion and step activity.
- **TMP117** for independent HIGH/LOW temperature alerts.

A motion event or thermal alert can open an Episode. Motion and thermal sources are represented as independent flags inside the same Episode rather than separate combined-state types.

The MPU6050 is not kept continuously active. It is power-gated and enabled only for selected motion bursts according to the configured acquisition level.

## Episode lifecycle

The active Episode state machine supports:

- Motion-only Episodes.
- Thermal-only Episodes.
- Motion + thermal Episodes via source flags.
- Motion quiet-time split.
- Thermal-normal split.
- Maximum-duration close.
- Hard close at the telemetry-window boundary.
- CARRY restart when a source is still active after the boundary.

At every telemetry boundary:

1. The final sensor samples are collected.
2. The currently active Episode, if any, is force-closed with `TELEMETRY_BOUNDARY`.
3. The closed Episode is converted to a digest.
4. If no Episode exists for the window, one baseline Episode is generated.
5. The telemetry-window snapshot is frozen.
6. Deferred runtime configuration can be applied at this safe boundary.
7. Still-active motion/thermal state is restarted in the next window with the `CARRY` flag.
8. The packet is queued for LoRaWAN transmission.

This makes each telemetry window self-contained while preserving continuity across windows.

## Telemetry V4

Wire protocol version: **6**

### Summary header — 19 bytes

| Bytes | Field |
|---|---|
| 0 | protocol version + message type |
| 1..2 | telemetry sequence |
| 3 | runtime config version |
| 4 | status flags |
| 5 | acquisition level / custom profile |
| 6..7 | battery voltage, mV |
| 8..9 | BMA456 step delta |
| 10..11 | accepted motion-pulse count in the window |
| 12..13 | telemetry-window duration, seconds |
| 14 | temperature sample count |
| 15 | dropped Episode count |
| 16 | transmitted Episode count |
| 17 | total packet count |
| 18 | suppressed-trigger count |

Temperature current/min/max are deliberately **not duplicated in the header**. Temperature is represented in the Episode records.

### Episode digest — 16 bytes

Each V4 Episode carries:

- start offset
- duration
- accepted pulse count
- mean inter-pulse interval
- suppressed-trigger count
- temperature minimum
- temperature maximum
- temperature at Episode end
- RMS dynamic acceleration
- peak dynamic acceleration
- peak angular velocity
- orientation change
- source/quality flags
- close reason
- MPU burst count

Episode temperature is quantized to 0.25 °C for the compact wire format.

### Episode flags

Flags include:

- MOTION
- TEMP_HIGH
- TEMP_LOW
- MPU_USED
- MPU_SKIPPED
- TEMP_VALID
- MPU_FAILED
- CARRY

### Close reasons

- `UNSPECIFIED`
- `MOTION_QUIET`
- `TEMP_NORMAL`
- `TELEMETRY_BOUNDARY`
- `MAX_DURATION`

## LoRaWAN packetization

The application keeps each V4 application payload at or below **51 bytes**.

- Summary header: 19 bytes
- Episode digest: 16 bytes
- Summary capacity: 2 Episodes
- Continuation header: 7 bytes
- Continuation capacity: 2 Episodes

Example: 8 Episodes are transmitted as 4 uplinks:

- Summary: Episodes 1–2
- Continuation 1: Episodes 3–4
- Continuation 2: Episodes 5–6
- Continuation 3: Episodes 7–8

The summary and continuations share the same telemetry sequence and expose packet/episode totals so the backend can detect missing fragments.

## Downlink management

The research release contains the functional downlink path with:

- atomic configuration validation
- duplicate transaction handling
- ACK/NACK response
- pending apply mask
- deferred sensor reconfiguration
- runtime config version tracking

Selected downlink scenarios were previously exercised on hardware, including uplink-period changes, acquisition-level changes, temperature limits, invalid values, duplicate transactions, and atomic rollback.

## Low-power work

The firmware uses STM32 STOP2 between application deadlines when radio and sensor state allow it.

A hardware issue found during bench testing was fixed: the ADC asynchronous clock based on PLLSAI1 is restored after STOP2 before battery measurements. This resolved zero-millivolt battery readings after wake.

## Decoder support

The repository includes updated decoders for:

- ChirpStack
- The Things Stack
- Bolus Downlink Configurator / telemetry toolkit

They support legacy telemetry and Telemetry V4.

## Validation status

Observed on hardware before the final V4 header repack:

- Telemetry V4 summary reception through ChirpStack.
- Episode force-close at telemetry boundary.
- CARRY across telemetry windows.
- Motion + thermal Episode behavior.
- Motion quiet split while thermal remains active.
- Multiple Episodes in one summary.
- Battery telemetry around the expected physical battery voltage.
- MPU-derived Episode motion features.

The final compact V4 header layout in this release has been exercised with decoder/toolkit vectors, but it still requires a fresh firmware build, flash, and end-to-end board/ChirpStack confirmation.

Host regression tests for the current V4 layout are present in the repository. No CI status is attached to this release commit, so this release does **not** claim a passing hosted CI run.

## Known research limitations

This release is intended for research and controlled bench/animal-study preparation, not production deployment.

Still requiring systematic validation:

- full host-test run on the release snapshot
- clean build and flash from the release snapshot
- final compact V4 header end-to-end verification
- 3–8 Episode continuation testing over real LoRaWAN
- long-run rollover/queue testing
- controlled motion-only / thermal-only / combined-event experiments
- physical power measurements through board current jumpers
- final antenna tuning and RF validation

## Reproducibility

For any experimental dataset, record at minimum:

- release/tag name
- exact commit SHA
- runtime configuration version
- acquisition level
- uplink period
- relevant temperature thresholds
- ChirpStack device profile / decoder revision
- firmware build configuration

This keeps experimental observations traceable to a specific firmware state.
